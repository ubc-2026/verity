Separate “will it happen?”from “how does it resolve?”

Verity reads a prediction market’s settlement rules, scores the resolution risk, buys research only to close a real gap through request-bound USDC payments, and checks that what arrived matches what was paid for.

The price says how likely the crowd thinks an event is. It says nothing about which report settles it, or whether a missing word in the rules decides the payout. Verity scores that second question with code rules, proposes the smallest purchase that answers it, and keeps every purchase inside the owner’s spending tiers. A wallet signature, not a voice, authorizes the larger ones. It places no trades.

    05 / Architecture
    Four layers, each with one job
    The analysis only proposes. A separate payment service holds the signer and decides. That split is the whole safety argument.
    
    
    
      
    Layer
    Name
    Responsibility
    Technology
    
      
    L1
    Brain
    Reads the contract, scores resolution risk, finds gaps, proposes purchases
    Gemini Exchange public API · verity-rules-v1 (code rules, no LLM)
    
      
    L2
    Wallet
    Pays for exactly the requested resource, once
    x402 · EIP-3009 · USDC on Arc Testnet
    
      
    L3
    Safeguard
    Enforces tiers, the 25 USDC budget and human approval
    Policy engine · ElevenLabs voice · wallet signature
    
      
    L4
    Auditor
    Matches each payment to a verified delivery
    QuickNode Streams · reconciler
    
    
    

    
    
      
    Module 1
    Hardened payments
    1. Canonicalize the request
    2. Hash it with keccak-256
    3. Sign an EIP-3009 authorization
    4. Merchant recomputes and compares
    5. Nonce blocks a replay
    payment service (separate from analysis/)
    
      
    Module 2
    Market risk analysis
    1. Read the event and terms link
    2. Inspect the settlement source
    3. Read bid, ask and volume
    4. Score four categories, 1 to 3
    5. List gaps and free checks
    analysis/verity/rules_analyst.py, live.py
    
      
    Module 3
    Voice spending approval
    1. Match the amount to a tier
    2. Check budget and allowlist
    3. Escalate 0.51–2.00 to the owner
    4. Owner signs with the wallet
    5. Deny or time out cleanly
    policy engine · ElevenLabs
    
      
    Module 4
    Reconciliation
    1. Ingest settlement events
    2. Accept the merchant delivery
    3. Verify the content hash
    4. Deduplicate by event and nonce
    5. Flag every discrepancy
    QuickNode Streams · reconciler

    Verification
    —
    
  
    

    



    
  
    
    
    
      
    Exact resource binding
    A payment is valid only for the request whose hash it was signed over.
    
      
    Bounded spending
    Every purchase sits inside a tier, the mission budget and, above 0.50 USDC, a signed approval.
    
      
    Verified delivery
    A merchant receipt is not proof. The content hash has to match.
    
      
    Independent audit trail
    Settlement events and deliveries are reconciled, and gaps are flagged.
